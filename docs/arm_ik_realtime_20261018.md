# 当前双 M6 IK 的 200 Hz 延迟分析与 CPU 编译实现

本报告针对单个双臂场景的在线跟随计算。远端CPU为Intel Xeon Platinum 8336C，GPU为A100；优化后计时使用CPU。200 Hz 原先表示 `dt=0.005s` 的模拟时间步；它没有自动保证一次调用能在5ms墙钟时间内完成。之前14秒视频计算2800步用了472.65秒，平均168.8ms/步；视频以模拟时间1倍速播放。

## 实测瓶颈

基线Slurm4217，在同一远端A100节点用当前源码、显式初角和安装变换构造 `ArmFollower`，预热后计时20步。各段边界同步CUDA；profiler独立采样，不把开启profiler后的耗时当作正常运行延迟。范围不含场景编译、渲染或策略网络。

|实现/阶段|平均双臂耗时|说明|
|---|---:|---|
|Torch eager CUDA整个step|169.92ms|约5.9个双臂更新/秒|
|其中两侧solve合计|149.82ms|约88.2%；每侧12次DLS迭代、每次5个候选|
|其中两侧耦合处理合计|9.67ms|每侧固定48轮二分，即使候选已经可行|
|额外FK和CPU轨迹记录|4.49ms|不在上面的step时间内|
|Torch eager CPU单线程step|86.44ms|仅换设备仍达不到5ms|
|Torch eager CPU四线程step|86.33ms|小矩阵没有受益于更多线程|

单个step的profiler记录了11652次 `cudaLaunchKernel` 调用（另有908条 `cuLaunchKernel` 事件，不将两种API事件简单相加作为唯一kernel数）。两侧合计24次6×6线性求解；每轮都调用串联7关节的FK、姿态误差、候选搜索，逐算子执行产生大量小kernel、tensor分配与Python调度。候选仅需末端姿态，却也计算雅可比和完整链位姿。多个 `torch.isfinite(...).all()`、布尔判断及线性求解检查会产生设备同步。渲染与记录不是主要瓶颈。

这组数据针对一个双臂实例；不能据此推断512环境批量训练的CPU/GPU吞吐优劣。

## 已实现的优化

新增 `tsensei_v3_2_pianist/mjlab_env/arm_realtime.py` 中的 `RealtimeArmFollower`，作为显式选择的单场景CPU实现。使用Numba原生编译，把小矩阵和循环留在CPU内，去掉逐算子Torch/CUDA调度；候选FK不再计算无用的雅可比/链历史。耦合候选已可行时直接返回，超界时继续原48轮可行前缀二分。

保留当前算法和执行合同：

- float64；每步每侧12次DLS迭代；5个线搜索候选，使用之前的参考解继续求解。
- 原URDF位置限位、SDK速度/加速度限值、离散制动距离、数值裕量和最终硬检查。
- `1.025×|J6|+|J7|≤110.5°`，原耦合可行性容差；不将约束降为软惩罚。
- 目标误差允许存在；执行的q/v/a来自限速轨迹，不把掌根直接传送到目标。
- 两侧均通过后才一起提交状态；第二侧输入非法或任一侧硬限失败时，不提交第一侧。
- 54维观察的内容及运动超限计分语义保持；单场景接口返回NumPy数组。

该初始组件验收阶段训练场景仍用Torch批量后端；后续场景接入见末节。没有改变奖励、动作范围、安装变换，也没有发送硬件命令。

## 初始组件的使用与限制

可复用验收入口：`scripts/benchmark_arm_realtime.py --reference-directory DIR --output OUT`，DIR应同时包含同一次当前生产回放的 `video_report.json` 和 `ik_trace_200hz.npz`。远端可选依赖安装在独立目录 `ik_realtime/deps`，Numba0.67.0 / llvmlite0.49.0；已有训练环境未修改。

应用程序通过当前options和已确认安装位姿构造 `RealtimeArmFollower(options, initial_poses, dt=.005)`，启动前调用 `warmup()`。控制循环调用 `step({side: (world_position, world_rotation)})`；世界目标由固定掌根参考加位移得到。上游仍负责原动作映射、20Hz目标更新/目标整形和准备段，不能把本组件当作上游合同的替代。渲染、磁盘写入、通信和可视化应在控制循环外异步消费状态；每5ms只读取最新目标、计算受限q/v/a并交给执行层。

目前证明的是服务器上单双臂**计算组件**在这些轨迹中的200Hz可行性。SDK传输/应答、真实控制器、操作系统最坏调度、长时运行、完整物理/碰撞查询和策略推理尚未包含；不能据此宣称整套系统硬实时。接入时应把通信算入5ms总预算并记录截止时间违约，启动编译完成后才允许控制；不能通过超时后补发多个旧命令追赶时钟。

如果优化目标转为批量GPU训练，应另测不同环境数，再考虑FK/候选搜索融合、`torch.compile`/CUDA Graph和设备端失败标志；删除同步之前必须保持双侧原子检查与失败拒绝。本轮没有以减少迭代、降低精度或跳过安全检查来提速。

### 当前优化候选与稠密跟随奖励

IK最多12轮，仅在同一加权位姿残差平方和≤1e-30时提前结束数值已收敛的求解；后续制动与q/v/a/CCS696耦合检查仍完整执行。场景微小矩阵计算改用float64定长循环。v7与v6相同14秒轨迹最大q差8.88317e-14rad、速度差2.4250e-11rad/s、加速度差4.8500e-9rad/s²、掌根位置差9.3259e-15m，目标数组完全相同。
