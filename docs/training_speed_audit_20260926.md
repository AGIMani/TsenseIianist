# Shadow 同步后训练变慢：2026-09-26 实测

## 结论

本次 5M 训练已于 2026-09-25 22:45 完成。主要耗时来自同步 Shadow 后增加的 SAC 更新次数；GPU 物理仿真已经并行。512 个环境每采集一个控制步，现在需要依次完成 512 次 SAC 更新，旧配置为 64 次。

这不是把 batch 缩小就能同比减少的工作：同机短测 batch256 每次更新约 3.805 ms，batch4096 约 4.357 ms。batch 缩小 16 倍，单次更新仅减少约 13% 时间。每次更新仍包含完整 Critic、Actor、温度优化和目标网络更新；前后更新依赖最新权重，不能直接把 512 次更新合成一次大 batch 后宣称算法相同。

所有 batch 行使用次数反而减少到旧配置的约 52.64%，但更新次数增加很多，说明不能用总 batch 行数单独预测墙钟时间。GPU 小矩阵计算、随机数／dropout、优化器、目标网络更新和主机调度都有每次更新的成本。

训练过程没有视频渲染；视频导出不是这 5 小时的组成部分。replay 仍驻留 GPU，现有证据没有显示发生 CPU 换页／显存溢出；容量增加本身不是 7 倍变慢的解释。

## 独立短测：时间具体花在哪

硬件 RTX PRO 6000 Blackwell，Torch 2.10，TF32 关闭，物理 graph／编译学习器／融合 Adam 开启；测量时没有并行的其他诊断 GPU 任务。

用最新 final 策略产生 16 组有效 transition，重复填满 replay，独立更新不保存权重。物理部分为 512 环境、每控制周期 10 个物理子步、12 次计时；学习器预热 32 次后，分 3 组各计时 256 次更新。两个 batch 测量均使用同一 Shadow 动作 profile，以比较计算尺寸的影响；不是重新跑一次旧训练。

| 部分 | 实测平均耗时 |
| --- | ---: |
| 512 环境 Actor 推理 | 0.493 ms／向量步 |
| 512 环境物理 | 28.763 ms／向量步 |
| 乐谱／奖励／观测等任务逻辑 | 2.662 ms／向量步 |
| batch256 一次 SAC 更新，含 replay 取样 | 3.805 ms |
| batch4096 一次 SAC 更新，含 replay 取样 | 4.357 ms |
| 512 次 batch256 更新，按短测换算 | 1.948 s／向量步 |
| 64 次 batch4096 更新，按短测换算 | 0.279 s／向量步 |

本次正常采集／更新步的学习器占比约 **98.4%**（不含评估、保存、replay 插入等）。即使把物理部分完全消除，也只能省正常步约 1.5%；再增加并行环境主要提高采集并行度，不能减少总共约 500 万次顺序更新。

边界：这是独立计时，并非长训练逐阶段的精确归因。显式同步计时会改变流水安排；重复 replay 内容不等于历史 replay；不比较新旧策略质量。replay 取样单独短测约 0.038 ms／batch256，已包含在更新耗时内，不能重复相加。

## 评估是否太频繁

本次为接近 Shadow 每 10,000 条采样一次评估，采用每 20 向量步一次，即每 10,240 条采样。489 次评估比旧 20 次多 24.45 倍。

日志已有累计吞吐，可还原相邻日志间隔。去掉启动期后，本次普通两个向量步的中位耗时为 3.899 s，经过评估后的对应间隔为 5.978 s；差值约 **2.079 s／评估**。据此估算累计约 1,017 s，即 **17 分钟／总耗时 5.1%**。这是基于日志差分的估算，不是原训练内的 profiler 精确值；最终评估、接触变化及保存会有少量差别。

保存频率两次相同，均 19 个周期检查点加 final。新日志中“评估＋保存”间隔并未出现大的额外台阶；不能把主要瓶颈归于写盘。旧评估与保存总是同一步，单靠旧日志不能拆分二者成本。

## 后续可怎么提速

### 保留 Shadow 学习预算的实现优化

- 当前只编译 tensor loss／backward，整个 SAC 更新块仍由 Python 调度；继续优化完整 learner 的图执行、批量生成随机噪声／dropout mask、融合目标网络更新，可减少小算子和调度开销，但须先做数值与恢复合同验证。本次尚未实现这些优化，不能承诺倍数。
- `SAC.update()` 每次最后的 `if not torch.isfinite(...).all()` 会读取 GPU 布尔值，形成主机同步。可研究把健康检查累积后在向量步末统一读回；这会改变错误检测延迟，需保留失败处理并验证。不能直接删检查后当作已解决。
- 评估改稀疏／并行安排可减少约 5% 的当前总耗时，但会降低评估曲线分辨率或增加资源竞争；**不能靠这一项恢复到 46 分钟**。

### 会改变已确认 Shadow 算法预算的选项

- 减少 `updates-per-transition`，例如从 1 降到 0.125，可以显著减少更新次数，但改变数据复用和收敛轨迹。
- 增大 batch 并减少更新次数，也改变优化器更新顺序和学习预算；即使总 batch 行数相同也不是等价替换。
- 放宽浮点精度、改奖励、缩小网络等分别改变数值或算法合同，不应混称为已经验证的无损性能优化。

因此本次仅分析和计时，没有擅自回退用户 2026-09-25 确认的 Shadow 更新预算。论文 pp.8–10／Table 2 的 batch4096、0.125 update/transition 与当前 Shadow 不同，差异已登记于 `docs/references/biomimetics_2026_610_notes.md`；不因速度问题自动切回论文方案。
