# 双卡加速幅度审计

2026-09-30。读取Slurm934等预算基准、935完整5M训练的原始日志、遥测和作业归档源码，仅在CPU上分析。没有提交新训练或更改运行参数。数值与输入SHA-256见[分析数据](dual_gpu_speed_audit_20260930.json)。这些实测对应TX/TY 1.2m/s；当前1m/s尚未重新测量。

## 结论

双卡采样／学习流水确实在工作。加速幅度有限有两个主要原因：

1. SAC更新仍全部运行在一张卡上，学习比采样约慢3.3倍。另一张卡只能重叠采样时间，不能把学习耗时减半。
2. 正式训练暂停学习进行99次评估，3个回合在单个独立环境里顺序执行。评估边界及其保存／管理开销约26分钟，占训练计时约35%，进一步稀释采样流水的整体收益。

跨卡同步／replay写入不是现有计时中的主要瓶颈；不能把GPU利用率接近100%解释为算力效率接近峰值。

## 1. 等预算单卡／双卡实测

作业934每组262144样本、42112次更新，两轮单卡／双卡交替执行。每轮取第190→510步的稳定区间，排除首轮编译、预填及末评估。

| 模式 | 第一轮样本/秒 | 第二轮样本/秒 | 平均 |
| --- | ---: | ---: | ---: |
| 单A100 | 1363.17 | 1360.72 | 1361.94 |
| 双A100流水 | 1744.28 | 1746.30 | 1745.29 |

实际稳定吞吐提升 **28.15%（1.2815倍）**，对应等样本稳定阶段耗时减少约22%。短训总墙钟比值1.84倍受冷／热缓存影响：首个单卡438.8秒，后一个单卡192.3秒；不能作为长期加速倍数。

第一轮双卡的每向量步（512条样本）计时：

| 阶段 | 耗时 |
| --- | ---: |
| 采集512条样本 | 89.22ms |
| 完成128次SAC更新 | 291.03ms |
| Actor快照同步 | 0.49ms |
| replay写入、检查和局部reset | 1.75ms |
| 实际稳定向量步墙钟 | 293.53ms |

采样的89.22ms全部被学习阶段覆盖。保持这些阶段耗时的理想串行／并行比值约为 `(291+89)/291=1.31`，与实测1.28接近；这是基于双卡阶段计时的估算，不是单卡独立阶段测量。

实现依据：`CollectorPolicy`复制Actor快照，`OneBatchPipeline`把第t批采样与第t−1批学习重叠；replay及唯一SAC学习器在cuda:1。两个Critic没有分配到两张卡，也没有多卡梯度并行。每512条新样本仍需128次顺序更新，完整运行共1,226,624次。

## 2. 完整5M的时间花在哪里

935作业总时长75分12秒；`summary.elapsed_s`为4491.64秒（74.86分钟），其起点在环境初始化之前，范围与Slurm时间略有差异。

| 累计量 | 秒 | 解释 |
| --- | ---: | --- |
| 学习回调 | 2853.34 | 47.56分钟，含55.24秒首次学习器构图 |
| 采样回调 | 773.37 | 12.89分钟，其中747.62秒与学习重叠 |
| Actor快照 | 4.78 | 全程总量 |
| replay写入／检查／reset | 17.35 | 全程总量，含跨卡数据进入replay |
| 上述阶段时间并集 | 2901.20 | 学习+采样+快照+commit−重叠 |
| 并集之外 | 1590.44 | 26.51分钟；评估、保存、初始化和其他管理开销 |

全程采样回调约96.7%与学习重叠，说明现有流水已经覆盖大部分可重叠采样。快照与commit共22.12秒，仅占总计时约0.49%；不能据此精确拆分纯拷贝耗时，但足以排除它们是数十分钟瓶颈的判断。

这些是带同步的主机回调计时，不是CUDA事件／内核profiler。`pipeline_step_wall_seconds`不含外部边界flush，不能直接用总耗时减去该字段，全部差额便归为评估。本次按累计回调并集做核算。

## 3. 评估使学习卡长时间闲置

实际共有99次评估：起始1次、每100向量步97次、末次1次；每次3回合，合计297回合。每回合183控制帧，约54351个逐步评估调用。

归档 `train.py` 的 `run_evaluation()`先排空待更新批次，再同步Actor，在采样卡执行 `evaluate()`。`evaluate()`要求一个独立世界，`for episode in range(episodes)`顺序运行三个回合；整个调用返回后才恢复训练。学习卡在这段时间没有更新工作。

原日志没有独立eval计时，因此采用以下可复核的差分：

1. 从训练日志 `transitions / loop_transitions_per_second`还原累计墙钟时间。
2. 取相邻日志差值，再扣除其间 `update+collection+snapshot+commit−overlap` 的计时增量。
3. 日志写在评估之前，故200→210、300→310等间隔包含评估；排除前200步的启动期。

| 间隔类型 | 数量 | 扣除采样／学习等之后的平均剩余秒数 |
| --- | ---: | ---: |
| 普通10步 | 860 | 0.0027 |
| 评估、没有保存 | 42 | 16.09 |
| 评估、保存best | 35 | 15.91 |
| 评估、周期保存 | 19 | 16.07 |

96个已覆盖评估边界累计剩余1537.74秒，平均16.02秒，已经解释了大部分1590.44秒阶段外开销。没有保存的边界同样耗时约16秒，因此评估是主要原因；不能把这些剩余时间称为逐内核精确评估耗时。

正式训练大致每训练100步约29秒，就插入约16秒评估。短基准只做起始／末次评估，而正式运行每100步做一次，两者端到端吞吐不能直接相互替代。

## 4. 遥测及互联证据

935每卡2246个约2秒间隔的遥测样本，覆盖启动、训练、评估及退出：

| 指标 | cuda:0采样卡 | cuda:1学习卡 |
| --- | ---: | ---: |
| GPU利用率中位数 | 37% | 99% |
| GPU利用率均值 | 43.10% | 62.26% |
| 利用率低于5%的样本占比 | 10.60% | 36.95% |
| 遥测显存峰值 | 5117MiB | 10283MiB |

学习卡高负载与闲置交替，符合训练／评估的执行结构；遥测不是SM占用率、FLOPS或带宽利用率，不足以证明学习器已达硬件上限。采样卡在学习期间等待也符合单批流水设计。

两卡NV12互联，P2P探针双向约200.1／195.7GB/s，结果校验通过。这是特定尺寸复制短测，不是训练传输带宽；配合快照／commit计时，目前没有互联拖慢全程的证据。

## 5. 为什么不能拿旧机器的55分钟直接比较

本机有同A100、同样本／更新数的短训对照，但没有同条件单A100连续5M的实测。旧本地单卡53～55分钟来自另一运行环境；仅用它与双A100约75分钟相除，无法衡量双卡流水本身的收益。

如果假定各阶段成本不变，把当前已重叠的747.62秒重新串行执行，可估得约87.32分钟，相对74.86分钟约1.17倍。这只是说明串行评估如何稀释收益的粗略模型，**不是已测得的单A100完整训练结果**。当前1m/s设置也没有新性能对照。

## 6. 优化优先级

1. **先优化评估执行**：将三回合评估改为三个独立环境批量执行，保留三回合统计、完整200Hz诊断、最低F1／碰撞门槛、best资格与评估频率。需要验证批量物理差异、各环境reset和指标汇总；不承诺逐位等价或3倍加速。当前单环境限制和大量`[0]`索引需要系统修改，不能只把num_envs改成3。
2. **再定位学习器内部耗时**：Slurm内短profiling拆出replay随机采样、网络前后向、Adam和graph提交。当前每128次更新仍逐次在主机调用采样与`graph.replay()`；可能有调度、小矩阵或内存访问开销，但现有日志不能确定其中主因。已有完整CUDA图与Adam优化，不应把“打开CUDA图”作为尚未实施的方案。
3. **评估频率作为独立取舍**：例如100→500步预计能减少约78次评估，按16秒/次粗估节省约21分钟；会改变选模和早停分辨率，须明确选择后再改。固定其余条件的估算不能作为保证，也不作为本次默认修改。
4. **跨卡拷贝／更深流水优先级低**：采样几乎已完全重叠，减掉全部已计快照／commit也只有约22秒。加大队列主要增加策略延迟，不能直接缩短单学习器关键路径。
5. **两卡同时更新同一策略需另测**：小型网络每次梯度同步可能抵消并行收益，不能承诺DDP翻倍。若目标是尽快完成多个独立奖励对照，两卡各跑一个单卡实验可作为吞吐方案，但需实测并控制执行方式，不能与当前双卡单策略直接混算。
