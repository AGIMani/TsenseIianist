# GPU训练吞吐与速度上限测试（2026-09-26）

## 范围

用户要求解释速度变化、继续检查稳定吞吐提升空间，并测试GPU最大训练速度。沿用此前“只加速，不改其他”的约束：正式`run.sh`、SAC、batch256、replay1M、FP32、每新样本1次更新、准备流程、奖励、碰撞和评估频率保持。不同环境数量仅用于诊断容量扫描，不是新训练默认。下面的“上限”指本次所测实现和条件的最好结果，不是显卡在所有算法上的绝对最大性能。

硬件为本机NVIDIA RTX PRO 6000 Blackwell，约96GiB显存；Torch2.10/cu128，原驱动和依赖未修改。各GPU实验串行运行；桌面进程继续存在，没有关闭用户程序、修改功耗或锁频。

## 为什么比旧训练慢

同样采集5,000,192条样本，旧46分钟实验实际更新593,088次；同步Shadow后更新4,995,193次，增加约8.42倍。旧batch4096、新batch256，不能用相同样本数推断相同计算工作或相同GPU效率。后来5小时34分钟是完整旧执行方式的实跑；新执行优化之后尚未完成新5M长训。

前次962条/秒来自40向量步短测，replay只写入20,480行，没有跨回合。它是排除评估的普通步骤速度，不等于进度条累计速度，也不是包含源码构建的总速度。本轮开始前没有本项目新长训进程，随后看到的训练进程是本次测速。

历史Shadow满库前1500–1900步中位1.9522秒/向量步，满库后2000–2400步1.9495秒，7000步后1.9490秒；未发现“replay填满导致历史持续掉速”的证据。历史reset额外中位约5.95ms，远小于单次完整更新块；具体窗口和排除规则见[历史审计](../preview/outputs/diagnostics/gpu_ceiling_20260926/history/history.json)。

## 当前默认512环境：延长到240步

使用真实`run.sh`，仅缩短运行长度为240步并关闭终端进度显示。共122,880条样本、117,881次更新、12次评估，512个回合正常完成，0截断。保留完整1M replay分配，实际写入122,880行；满库另做独立学习器测试。

| 口径 | 实测 |
| --- | ---: |
| 普通训练步骤中位吞吐 | **967.6条/秒** |
| 普通步骤吞吐10%–90%分位 | 962.6–973.3条/秒 |
| 普通向量步中位耗时 | 0.5292秒 |
| 含初始化、12次评估及最终保存 | 159.93秒，768.3条/秒 |
| 再计入源码重建和进程启动 | 174.79秒，703.0条/秒 |
| 周期评估额外中位耗时 | 约2.744秒/次 |

普通步骤从第40步以后选取，排除包含评估和reset的区间，共89个窗口；不是挑最快的单步。相较前次962.1条/秒，没有测到继续掉速。按本轮普通步骤和评估外推，当前5M约108.5分钟，取代前次短测约102分钟的估算；仍非5M实跑，尚未覆盖全部训练接触分布与周期存盘。评估仍每20向量步执行，没有为了提速降低频率。

### GPU状态

从监控开始20秒后统计，GPU-util中位96%，功耗中位约230W，显存约16.36GiB，温度中位54℃、最高58℃，SM频率中位2820MHz。运行中读取的降频原因均未激活，未发现温度或600W功耗限制成为本次瓶颈。监控包含评估，末尾进程退出后的采样也保留，未通过过滤低利用率样本抬高结果。

GPU-util是采样期间“有kernel正在执行的时间比例”，不是计算单元全部满载的比例。因此96%与未达到600W并不矛盾，也不能据此判定显卡算力已完全用尽。[NVIDIA官方定义](https://docs.nvidia.com/deploy/nvidia-smi/#utilization)

## 满replay的独立学习器上限

固定1181维观测、47动作、batch256、相同网络和FP32，用1M条独立初始化的有限合成transition测试，replay实际分配及初始化9.646GB。每项预热后测3组、每组512次顺序更新，CUDA事件与主机计时均同步。合成数据隔离学习器，不代表真实策略收敛。

| 当前已启用执行方式 | 实际有效replay行数 | 中位完整SAC更新/秒 |
| --- | ---: | ---: |
| CUDA graph＋256线程Adam布局 | 128,000 | 1045.8 |
| 同上 | 1,000,000 | **1050.2** |

两者差异小于0.5%，没有测到满replay导致掉速。此处含真实随机取样、原Critic/Actor/温度和目标网络更新，不是仅神经网络前向速度。

在本次学习器实现、每条样本1次更新的条件下，即使暂时忽略仿真和评估，约1050条/秒也是实测学习端给出的近似吞吐界限。默认完整训练普通步骤967.6条/秒已约为它的92%。增加并行环境不会取消更新量：

`采样吞吐 ≈ 环境数 / (该批环境采集耗时 + 环境数 × 单次SAC更新耗时)`

因此不能把更多环境的纯采集速度直接当完整训练速度。1050是当前实现/输入形状的短测结果，不是GPU硬件或所有可能优化的理论极限。

### 剩余学习器开销与候选

20次更新的GPU活动分析：矩阵主核约52.2%，矩阵辅助约8.1%，编译后的逐元素/归约约14.8%；Adam约6.65%，replay gather约2.51%。活动时间相加为818.7微秒/更新；分析器会扰动执行，不能用这个数替代约0.952ms/更新的独立墙钟计时，也没有测出硬件SM占用率。

保持原Adam数学及数据类型，诊断尝试128、64和512线程布局；满库约1046.5、1023.0、1037.3更新/秒，均没有超过当前1050.2的可靠收益。所有候选仅在独立诊断中运行，没有修改正式包或默认开关。

数值边界也保留原始失败证据：这些分块候选相对当前256线程布局累计128次更新，参数、Adam状态、指标和RNG逐bit一致；当前布局对原fused Adam的更长合成压力对照中，参数最大差仍为1.19e−7，但2,708,674个moment元素中有2个超过原严格绝对/相对容差，moment最大绝对差2.29e−5。没有放宽阈值或将其标作全部通过；原布局本来就不承诺长期逐bit一致，本轮也未新增启用任何候选。

## 环境规模扫描：纯采集容量

从同一个当前短训检查点读取策略，128至4096环境逐点独立进程测试。每点预热1个178步回合，计时2个完整回合（356向量步），含真实准备、奖励、观测及reset；再用前一阶段记录的动作做2回合环境计时。每个进程结束后释放Torch/Warp显存，各点没有同时争用GPU。

| 环境数 | 策略＋环境，条/秒 | 环境重放已记录动作，条/秒 | 策略采集结束时进程显存 |
| ---: | ---: | ---: | ---: |
| 128 | 4,299 | 4,369 | 2.13GiB |
| 256 | 7,790 | 7,929 | 3.44GiB |
| 512 | 13,779 | 13,927 | 6.11GiB |
| 1024 | 22,274 | 22,692 | 11.38GiB |
| 2048 | 31,588 | 31,921 | 22.04GiB |
| 4096 | **37,978** | **38,131** | 42.98GiB |

六点均完成，没有容量溢出或非有限状态。这里不包含replay存储、反向传播、SAC更新、评估和保存，**3.8万条/秒不是强化学习训练速度**。显存为阶段末观察到的进程用量，包含暂存动作，不是连续监控的峰值；也未计入完整训练还需要的replay和optimizer。

512环境采集约37.16ms/向量步，而512次学习器更新约488ms，学习耗时占这两项串行成本约93%。4096纯采集仍能增加，但改善采集并不会消除学习瓶颈；本轮没有继续消耗资源探测显存分配的绝对极限。

首次诊断在CUDA尚未初始化时重置峰值统计报错，发生在环境创建前；只修复诊断脚本初始化顺序后重跑，失败记录与成功v2记录都保留，没有修改场景容量。数据及重现脚本见[容量扫描报告](../preview/outputs/diagnostics/gpu_capacity_20260926/collection_scan_v2.json)。

## 确定性策略前向图候选

保持原Actor完整forward，50个真实1181维观测＋50个随机输入，batch1/512各100组对照；CUDA图动作逐bit相同，参数原址更新后结果正确，恢复参数正确，三个RNG状态均不变。

单环境、每次调用同步的中位延迟98.56→37.96微秒，局部约2.60倍。但整曲178次调用合计仅约10.8ms节省，对约2.744秒评估只约0.39%，还未做整评估实际集成计时。batch512也仅测试确定性前向，不能当作随机训练采样的提速。本轮保留诊断，不加入收益很小的新正式执行路径。

更大的剩余候选是环境/奖励/评价的张量调度，尚未图化验收。不能直接捕获整个环境：历史观测会重绑定，返回观测要求独立存储；复用一个静态输出可能在下一step覆盖replay的旧state，必须先保证时序、局部reset及旧/新观测独立性。没有为了速度关闭检查或改变奖励。

## 完整训练规模复核：相同样本、更新和评估预算

额外跑2048环境×60向量步，与512环境×240步一样采集122,880条样本、完成117,881次SAC更新。评估间隔从20向量步对应调整为5步，仍每10,240条样本评估一次、共12次；保存间隔按相同样本数换算。20个关键配置字段、源码、准备合同、奖励及SAC相等已断言。日志仍每2向量步记录，故大规模组日志较少，记录差异不藏匿。

| 完整训练实测 | 当前默认512环境 | 规模诊断2048环境 |
| --- | ---: | ---: |
| 普通步骤中位吞吐 | 967.6条/秒 | **1010.4条/秒** |
| 普通步骤10%–90%分位 | 962.6–973.3 | 1009.3–1012.3 |
| 含评估/初始化/最终保存耗时 | 159.93秒 | 156.96秒 |
| 上一行对应总吞吐 | 768.3条/秒 | 782.9条/秒 |
| 再含源码/进程启动耗时 | 174.79秒 | 171.73秒 |
| 观察到的设备总显存 | 16.36GiB | 32.06GiB |

普通步骤仅提高**4.43%**，短跑总时间仅缩短**1.86%**（总吞吐提高1.89%）。这是本次所测完整训练中的最高普通步骤吞吐；未实跑4096环境的完整SAC，也不宣称1010是所有实现的绝对极限。独立学习器约1050更新/秒与这个结果吻合。

2048组每环境只走60步，训练中未跨178步reset；其reset由前述完整回合容量扫描覆盖，512组实际完成512个训练回合。不同环境数改变采集后集中更新的分组及随机探索在每个世界覆盖的时间，不能称为完全相同训练轨迹或学习效果。**正式默认保持512**，没有为很小的速度收益自动改变用户已确认的并行规模。

## 结论与后续边界

- 未测到当前默认继续掉速：约968与前次962条/秒基本一致。显示的约768是包含评估的总吞吐；与旧46分钟比较则还涉及8.42倍更新次数，不能混为一谈。
- 本次现有实现的最高完整训练普通步骤约1010条/秒，发生在2048规模诊断；当前固定512约968。满replay学习端约1050，更多环境很快遇到学习器瓶颈。
- 未采用任何新正式执行优化：Adam分块没有可靠收益，Actor局部提速对整评估收益很小。正式SAC、batch、精度、更新比、奖励、碰撞、准备流程和512默认均保持。
- V32-PERF-01保留：下一步有效候选是学习器矩阵/归约实现和完整评估的张量调度；需验证数值、RNG、terminal/reset及旧/新观测独立性。没有通过TF32、减少更新或降低评估频率获得本轮结果。
- 本轮没有新开5M长期训练；短测不证明收敛、消除误触或所有长期接触/吞吐稳定。不同规模结果也不能直接证明大规模训练质量。

## 复测入口

在独立项目根目录执行：

```bash
python3 preview/scripts/benchmark_training_speed.py \
  --output preview/outputs/diagnostics/my_gpu_benchmark --vector-steps 240
python3 preview/scripts/analyze_training_speed.py \
  preview/outputs/diagnostics/my_gpu_benchmark
```

输出目录必须为新目录，防止覆盖证据。第一个入口调用真实`run.sh`并以200ms间隔记录GPU指标，额外参数放在`--`之后；第二个入口从原有metrics恢复区间耗时，不修改训练源码或日志公式。短训权重仅验证执行和测速，不能作为新策略已收敛的证明。
