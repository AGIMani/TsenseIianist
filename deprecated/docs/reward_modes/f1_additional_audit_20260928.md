## 2. 优先级最高的新发现

### 2.1 随机 warmup 没有覆盖任何演奏帧

当前 512 个环境同时从谱面第 0 帧重置，前 20 控制帧是准备期。`warmup_transitions=4999` 对应所有环境的前 9 个完整控制帧和第 10 帧的一部分，合计仅 0.5 秒；全部是空谱。

| 已保存配置与推导 | 数值 |
| --- | ---: |
| 并行环境 | 512 |
| 准备期 | 20 帧 / 1 秒 |
| 随机动作 transition | 4999 |
| 随机 warmup 中音乐目标 transition | **0** |
| 第一个开始学习的 transition | 5000 |
| 首个音乐 transition 到达前的更新 | **1310** |
| 每环境先覆盖完整 178 帧所需 transition | **91,136** |

计算为 `floor((20×512−4999)×0.25)=1310`。实现见 `rl_torch/train.py:warmup_action_count/updates_this_step/training_action`，以及训练循环同步 reset。旧单环境 4999 条样本会覆盖约 250 秒；相同总样本 warmup 在并行环境中并不具有相同曲目覆盖。

这不是“后来完全没有探索音乐”：初始温度为 1 的 SAC 随机策略仍会探索，训练最终覆盖了整首乐曲。它意味着学习初期 critic/replay 只见准备期，且音乐段没有经历同一随机 warmup 覆盖。这可能降低样本效率，不能凭这一事实断言它造成了本轮 0.97884 的上限。

**建议下一组独立对照**：新训练按谱长确保 replay 至少覆盖一次整曲，再启动学习；warm-start 时可用父策略预填整曲，避免用完全随机动作毁掉有用分布。若采用随机错峰或随机谱面起点，还要重新定义物理起始姿态，不能只改 score index。不要擅自改变当前已经确认的 4999 / 5000 / 0.25 设置，也不要将增加预填描述为免费提速。

### 2.2 提前定位会削弱同一帧内的当前指法奖励

`mjlab_env/fingering_experiments.py:42–59` 的公式是：

```text
R_finger = (Σ当前距离分 + 0.5 × Σ未来接近分) / (当前分配数 + 未来分配数)
```

当前与未来共享分母。比如 1 个当前用指加 2 个将用指，当前用指距离项的系数从 1 变为 1/3。未来单项乘了 0.5，并没有消除这个分母稀释。

实际 158 个音乐帧中有 149 帧有目标；其中 **45 帧**同时有未来空闲指目标，当前用指整体份额最低 **1/3**。漏掉的短 D5 在第 133 帧有 2 个当前目标、2 个未来目标，当前份额为 **1/2**；第 134 帧为 3 当前、1 未来，份额为 **3/4**。

这是有界共享预算方案的真实行为，不是越界或实现与注释不一致。它可能使快速过渡时“先定位下一音”与“弹好当前音”发生竞争，需要对照验证因果。

**建议候选**：保留总指法上限 1，为当前按键保留固定优先预算，把少量剩余预算给未来定位；只有空谱时才独立给未来接近分。应作为独立奖励实验，不与本轮两个按键奖励修复混成一组，不直接增大 humanoid 或总指法权重。

### 2.3 那个完全漏掉的 D5，策略本身没有给出相邻成功音相似的关节目标

直接按检查点中保存的 `action_contract.channels` 将原始 action 映射为请求角度，无需估计腕部世界坐标：

| 音乐起始时间 | D5 命中 | 右食指 MCP 请求 rad | 右食指 PIP 请求 rad |
| --- | --- | ---: | ---: |
| 6.30 s | 是 | 1.083 | 1.087 |
| 6.35 s | 是 | 1.051 | 0.811 |
| **6.65 s** | **否** | **0.249** | **1.476** |
| **6.70 s** | **否** | **0.102** | **1.483** |
| 6.80 s | 是 | 1.094 | 0.947 |
| 6.85 s | 是 | 0.786 | 1.108 |

因此“腕部限速太低导致本来正确的指令无法执行”不是唯一甚至不是最直接的解释。漏音时四指弯曲组合明显不同，而不是仅在同一个 MCP 请求目标上差一点物理行程。这也不证明单独把 MCP 拉到 1 rad 就能安全按对：指尖位置取决于全指、腕部和接触。下一步应针对**所有短音**记录每子步指尖—目标距离、实际/请求关节、接触体与键程，区分策略未形成按压动作和正确动作被卡住，避免为 D5 写专门范围。

## 3. 乐谱输入的通用问题：重复短音可以被删除

`music/piano_roll.py:97–117` 把开始向下、结束向上量化。`music/midi_file.py:335–343` 随后判断“上一原始 piano-roll 帧已有同键，当前帧又是 onset”，将当前帧跳过，用一个空帧区分连续同键。

在真正的 Composer 环境中复现以下 C4 输入：

| 原 MIDI 两次同键 | 原始有音帧 | 转换后有音帧 | 后果 |
| --- | --- | --- | --- |
| `[0,.10)`、`[.10,.15)` | 0,1,2 | **0,1** | 第二音完全消失 |
| `[0,.10)`、`[.10,.20)` | 0,1,2,3 | **0,1,3** | 第二音起音晚一帧 |
| `[0,.099)`、`[.101,.149)` | 0,1,2 | **0,1** | 有真实 2 ms 间隔，第二音仍消失 |

这是可验证的输入表示限制，不是策略漏按。原始 piano-roll 保证每音至少一帧，但后续去重会把这仅有的一帧删除；因此不能声称输入任意带指法 MIDI 就一定完整训练所有音。

**对本曲的影响必须分清**：34 个音都仍有目标区间；完全漏按的短 D5 第 133/134 帧未被删除。下一次 D5 原起音 6.791667 s，被向下量化到 6.75 s；前一次 D5 的结束已向上延到 6.75 s，所以 onset 帧 135 被置为空，下一帧 136（6.80 s）才作为目标。相对原 MIDI 晚了约 8.33 ms，不等于原始音乐晚了整整 50 ms。

**建议**：先增加训练前音符覆盖报告，列出被移位/完全消失的音与同指冲突，对消失音明确报错。重新定义释放间隔放在哪一帧，或提高曲谱/控制时间分辨率，会改变任务目标合同，应另立版本、另做对照；不能偷偷删掉去重让两个重复音变成一个长按，也不能改旧目标后直接称 F1 提升。

本曲同时验证：同一帧同一指多键冲突 **0**，同一键被多个指分配冲突 **0**。不能用“指法冲突”解释当前 D5 失分。

## 4. 观测与修改奖励后的迁移边界

### 4.1 奖励是策略的输入，改奖励即会改变回放轨迹

当前 `source_runtime.environment.action_reward_observation=true`。`MusicTaskLogic.advance()` 把本步总奖励写入 `last_reward`，`frame()` 将它拼入下一步观测（`task_logic.py:110,151,158`）。

因此本轮两个奖励修复不仅改变 TD 学习目标，也会在**尚未进行任何学习更新**时改变旧 actor 的下一步输入。旧 best 的新奖励零更新回放不能保证仍为原 F1；不同轨迹不能简单归因为迁移训练变差，也不能只用旧轨迹重算奖励来宣称新策略改善。正确验收需同时保留：

1. 归档源码 + 原奖励的父模型基线；
2. 新源码 + 新奖励、相同权重的零更新基线；
3. 明确权重迁移后的训练/评估。

不删除 reward 观测槽、不静默加载新源码到旧 checkpoint；这次发现属于验证约束，不自动授权观测设计变更。

### 4.2 单帧位置观测没有速度，当前指法也不显式包含每指键号

当前 `frame_stack=1`。`task_logic.py:110–115` 提供手关节位置、琴键位置、上次动作和奖励，但不含手指/琴键速度。处于同一浅按位置、正在向下运动和正在弹回的键，对未来数毫秒阈值行为不同；现有观测不完全确定这些状态。上次动作有帮助，但不等于真实速度。

当前指法基础槽只有十指使用标记；50 维提前定位新增字段仅针对**当前空闲**且即将使用的手指。手指一旦使用，未来目标槽被清零，当前“哪一指对应哪一键”主要由固定曲谱与几何历史隐含表达。对于任意新曲、换指或相同和弦不同指法，当前编码存在状态混淆风险。

这些是表达能力限制，不是证实本轮必然漏键的原因。可选速度/少量历史、明确当前指—键目标能够作为后续单独观测版本测试；会改变输入维度/模型合同，不应直接用旧 1231 维权重冒充兼容恢复。论文 §2.5 pp.7–8 明确包含速度和未来指法，但本次未自行采用论文设计。

## 5. 评估不能只看一个 F1

### 5.1 20 Hz 高分仍可隐藏子步迟按

本轮保存 best 的音乐 mean-frame F1 为 0.978843，200 Hz 音乐 micro-F1 为 0.938824。当前 `EvaluationTracker` 最佳模型按 `music_only_f1_min`，完成目标的 micro 条件也是 **20 Hz**。子步指标已记录，但没有成为该门槛。这不是计算 bug，也不是 20 Hz 和 200 Hz 必须数值相等；它说明达到现有 0.99 不自动意味着 200 Hz 音符覆盖也达到 0.99。

继续报告既有两种 F1，同时看原 MIDI 起落误差、短音命中率与实际拖尾，不更换原 F1 定义来获得漂亮数字。若新增子步达标门槛，要独立配置并明确其与原曲时间量化的关系。

### 5.2 最后一个音没有松键尾段

当前 158 音乐帧最后一帧仍以 C5 为目标，episode 随即结束。视频 C5 仍按下，之后没有目标为空的真实训练帧；最后音何时松开因而没有被训练/验收完整覆盖。视频中的 end hold 是显示用途，不能算成释放成功。

末帧 observation 保留最后目标窗；环境 discount=1，SAC 仍 bootstrap，这是既有 CPU/Shadow 兼容合同，不是当前代码漏乘 `1−terminated`。若希望训练最终释放，增加显式静音尾段与其目标定义比误改所有 terminal discount 更直接。论文 §2.3 p.6 使用 2 s 静音尾段，但未授权为此自动追加 2 s、改终止或 bootstrap。

### 5.3 掌壳诊断范围需补齐

旧 `KeyContactDiagnostics` 只按 palm/thumb/index/mid/ring/pinky 子串识别手部，遗漏 A3.2 的 `base_link` 掌壳。`key_underside=0` 因而只说明已识别几何没有这类接触，不能作为全手未卡键证据。**主任务本轮已补齐明确 `base_link_collision_` 名单，并完成 CPU/GPU 诊断验收**；没有将任意左右前缀的 wrist/mount/visual 全视为手指接触，也没有改实体碰撞物理。旧源码归档和旧评估数字保留原范围，不因新诊断修复而追认为全手安全。

## 6. 已排除的实现错误

- `train.py` 先将 `result.observation` 存入 replay，再对完成环境 reset；没有把 reset 初态误当 terminal next-state。
- `MusicTaskLogic.observation()` 返回克隆，replay 插入复制数据，后续 reset 不改写已存 transition。
- 先用 `applied_index` 计算本次奖励/目标，再推进 index 并输出下一观察；末端 actual 对应刚执行区间目标，不能为了时序表象额外平移目标一帧。
- 当前 reward history 子步最后状态与 20 Hz 端点在此前同轨迹核对中一致，没有发现错取了另一环境或前一控制帧。
- 控制 limiter 的上次实际目标包含在 action 观测；当前 idle/active 护指投影均明确关闭，不存在本轮策略被默认护指投影阻止按压的证据。
- 本曲没有同指多目标或同键多指标签冲突。
